# Bug fix

証拠のない修正を入れない。修正の一行ごとに、実行時の証拠まで辿れること。

1. 自分で再現する。ユーザーに再現を頼むのは、自分の手が届かない具体的な理由があり、届く限り試した後だけ。再現しなければ、トリガを合成する、条件を絞る、計装を足すのいずれかで再現させる。
2. 原因を仮説で絞る。候補を挙げ、残りの範囲を最も大きく削る分け方から実行時の証拠（ログ、計装、実行結果）で潰していく。コードを読んだだけの推測で決めない。生き残った仮説の機構を、実行時の証拠で確かめてから修正に進む。
3. 修正は最小にする。「念のため」の修正は仮説であり、入れない。証拠が仮説を否定したら、その仮説で入れた変更を戻す。
4. 修正を委譲するなら、`worker` に `worker-advisor` Playbook を指定する。ブリーフには再現手順、確定した原因、触る範囲を渡す。
5. 元の再現手順を、再現したのと同じ環境で再実行して通ることを確かめる。判定できなかった、または別の環境での確認は合格にしない。ユニットテストの成功は分岐の挙動を示すだけで、不具合が消えた証拠にならない。
6. 失敗する再現テストを、修正より前に置いて失敗を確かめる (`red-test-first`)。統合テストが重いなどテストにするのが高コストな場合は、省く理由を返答に書く。

## 返答

壊れていたもの、根本原因、修正、確認の方法を述べる。失敗時と成功時の再現の出力はそのまま貼る。
