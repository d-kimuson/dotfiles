# Lean Spec

仕様を Lean で書いて証明し、実装との差分テストで実装が仕様に従うことを確かめる。Lean のコードは人が読まない前提にし、人は doc コメントから生成した Markdown で仕様を読む。

  書き方: 対象を「〜を変える (例: 料金の計算を変える)」の形で 1 項目ずつ書き、置くディレクトリを書く。lakefile.toml の `globs` と、Feedback Loop の `lean-spec.ts` に渡すディレクトリを同じものにする
-->

## 配置

仕様は、それが定める実装の隣に同じ名前で置く。

```text
src/cart/
├── cart-total.ts               # 実装
├── cart-total.lean             # 仕様と証明
├── cart-total.lean.md          # cart-total.lean から生成した仕様 (手で編集しない)
└── cart-total.oracle.test.ts   # 実装と仕様の差分テスト
```

## 書き方

- ファイルの先頭に `/-! … -/` で、何の仕様かと、それを実装するファイルを書く。
- 公開する宣言 (`def`、`structure`、`inductive`、`theorem` など) には、`/-- … -/` でその意味を自然言語で書く。ほかの定義を使うなら、その名前 (`Pricing.discounted` など) で参照する。定理の doc には、証明の方法ではなく主張を書く。
- 要求の文書の各ルールと、境界での振る舞い (しきい値のちょうど、空、上限) を定理にする。定義を書き写しただけの仕様は、実装と同じ誤りを含みうる。
- 証明のためだけの補助の宣言は `private` にする。生成する Markdown に載らず、doc も要らない。
- 守るべき条件は `Prop` を返す定義で書く。生成する Markdown の「制約」に並ぶ。
- 宣言の主張を変えたら、同じ変更で doc も直す。doc と主張の食い違いは機械的には見つからないので、レビューで確かめる。
- `sorry`・`admit`・`axiom` は残さない。前提が要るなら定理の仮定にする。

## 生成と検査

Lean のファイルを変えたら、`node scripts/lean-spec.ts doc <dir...>` で隣の `.lean.md` を書き直し、同じ変更でコミットする。`node scripts/lean-spec.ts check <dir...>` は、doc のない公開の宣言、`sorry`・`admit`・`axiom`、生成し直していない Markdown、元の Lean がなくなった Markdown を報告する。`lake build` は証明を検査し、`sorry` は警告にしかならないので、両方を回す。`spec/` は仕様ではなく oracle なので、`lean-spec.ts` に渡さない。

## 差分テスト

`lake build` は `spec-oracle` (`spec/Oracle.lean`) も作る。`.lake/build/bin/spec-oracle` は標準入力から 1 行に 1 つ `{"fn": <宣言の名前>, "args": <引数>}` を読み、仕様の定義で評価した結果を 1 行の JSON で返す (評価できなければ `{"error": <理由>}`)。

実装を仕様と突き合わせるには、その定義を `spec/Oracle.lean` の `evalCase` に足し、実装の隣に差分テストを書く。差分テストは、このリポジトリの言語とテストランナーで、次をすべて満たすように書く。

- property-based testing で入力を生成し、同じ入力を実装と `spec-oracle` の両方に渡して結果を比べる。
- 生成する入力は、Lean の型と制約 (`Prop`) が許す範囲に合わせる (`Nat` なら 0 以上の整数)。実装の型が表せない値 (精度を超える整数など) は生成しない。制約の外の入力を実装が受け付けるなら、その扱いを仕様に足すか、実装で拒否する。
- 仕様の境界 (しきい値、0、上限) は、一様な乱数ではまず当たらない。入力から導かれる値 (割引後の金額など) が境界ちょうどとその前後になる入力も、狙って生成する。
- 入力と結果を、Lean 側の `FromJson`・`ToJson` の形 (structure はフィールド名をキーにしたオブジェクト) と実装の値との間で変換する。変換は差分テストの中に閉じ、実装に持ち込まない。
- `spec-oracle` が `{"error": …}` を返したら、比べずにテストを失敗させる。`spec-oracle` がなければ、`lake build` を案内して失敗させる。
- 食い違ったら、入力、実装の結果、仕様の結果を報告する。

食い違いが見つかったら、要求 (仕様の元になった文書やユーザーの判断) に照らして、実装と仕様のどちらが誤りかを決めて直す。要求から決められなければ、失敗するテストをコミットせず、反例を添えてユーザーに判断を求める。
