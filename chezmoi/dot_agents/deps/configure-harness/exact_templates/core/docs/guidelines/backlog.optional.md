# Backlog

タスクを確かめ、起票し、状態を更新するときの置き場所と書き方。

## 置き場所と操作

<!-- decision: backlog
  決めること: Backlog の置き場所と、一覧・起票・更新の操作
  観察: GitHub Issues、GitHub Projects、Linear、リポジトリ内のファイルなど、タスクを管理している場所。リモートがなければユーザーに聞く
  書き方: 置き場所を 1 文で書き、一覧 (優先度順、状態ごと)・起票・状態の更新・コメント・クローズの操作を、コマンド (`gh issue list --label ...` など) を添えて 1 操作 1 項目で書く。リポジトリ内のファイルで管理するなら、1 タスク 1 ファイルにし、ファイル名 (`backlog/<番号>-<slug>.md` など)、状態・優先度・ブロックを書く front matter、一覧のコマンド (`grep`)、コメントとクローズの書き方 (本文への追記、ファイルの削除か `status: done`) を書く
-->

## 状態と優先度

<!-- decision: backlog-states
  決めること: タスクの状態 (Ready、進行中、ユーザー待ちなど)、優先度、ブロックの関係を何で表すか
  観察: 使っているラベル、Projects のフィールド、Linear の状態と優先度、ファイルの front matter。issue 本文での依存の書き方 (`blocked by #12` など)
  書き方: 状態、優先度、ブロックの関係のそれぞれを、何で表すか (ラベル名、フィールド名、本文の書き方) と 1 行の意味で書く。既存の運用がなければ、ラベル (`status:ready` など) と本文の `Blocked by #<番号>` を推奨にする。ユーザーのタスクの表し方 (assignee、ラベル) も書く
-->

## 起票

- 要求 (誰の何を解決するか)、受け入れ条件、ブロックしている・されているタスクを書く。
- 判断を求めるタスクには、判断すること、選択肢、それぞれのトレードオフ、推奨とその理由を書く。受け入れ条件には、判断が決まった後に何が終わればよいか (決めた選択肢の実装、ADR など) を書く。

## Ready
