詳細より先に全体、散文より先に構造、抽象より先に具体。読み手は長い文章を頭の中で再構築するのが苦手で、構造・関係・対比が空間に置かれていると速く正確に読める。
## 1. 全体マップを先に置く
本文に入る前に、全体が一目で掴めるものを置く。構造図・フロー図・全体一覧の表・位置づけを示す 1 枚のいずれか。読み手が「いまどこの話か」を見失わない足場にする。
長い文書では、各セクションの冒頭にもその節の位置づけを 1 行で書く。
## 2. 散文を空間化する
段落が 3 つ以上続いたら、構造を持たせられないか疑う。
- 並列の列挙 → 箇条書き
- 属性を持つ列挙・数値の比較 → 表
- 選択肢の比較・トレードオフ → 比較表（行 = 観点、列 = 選択肢）
- 対立・変化 → Before/After の対比レイアウト
- 包含・階層 → 階層箇条書き
文章として残すのは、判断の理由・文脈・ニュアンスなど、構造化すると失われるものだけ。
## 3. 関係・流れは図で描く
複数要素の関係（依存・階層・所属）、時間や状態の遷移、分岐のある判断、「こう見えるが実体はこう」のズレは図にする。**迷ったら描く。**
- 説明の中で読み手が最もつまずく一点は必ず図にする。「自分が理解するのに一番時間がかかったところ」と一致することが多い
- 全体マップ（§1）も図が効くことが多い
- 図の直前か直後に、図が示していることを 1 文で書く。図だけを置いて解釈を委ねない
ただし図が効かないものに図を使わない。並列の列挙・数値の比較は §2 の箇条書き・表に落とす方が速く読める。
## 4. 具体例・Before/After を先に
抽象的な説明・方針・原則は、具体を先に見せてから述べる。
- コードの変更 → Before/After の対比
- 仕様・挙動 → 具体的な入力 → 出力の例
- 概念・方針 → 実在のシーンや実例
抽象論だけの段落を作らない。
## 5. 媒体別の出し方
- **投稿物（GitHub の PR / Issue / md、Artifact）**: Mermaid で描く（§6）
- **セッション（ターミナル）出力**: Mermaid は描画されない。関係・流れは罫線の ASCII 図か表で表す。図が複数要る・1 枚で表せない複雑さなら Artifact にしてリンクを渡し、ターミナルには要旨を残す
- **Mermaid 対応が不明な投稿先（esa・Jira・Confluence 等）**: 本番投稿前に 2 ノードだけの小さな図で試す。壊れた図は無い方がましなので、確認できないなら表に落とす
- 投稿後はブラウザで実際の見た目を確認する。記法が正しくても、日本語ラベルの折り返しや横幅で読めないことがある
## 6. Mermaid の落とし穴
- **ラベルは必ず `["..."]` でクォートする** — `(`、`)`、`:`、`/`、`,` が入るとパースエラーになる。エッジラベルも `-->|"..."|` とクォートする
- **ノードは 7 個までを目安にする** — 超えるなら図の粒度が細かすぎる。1 段上の抽象度で描き直す
- **日本語ラベルは横に伸びる** — 12〜15 文字を超えたら `<br/>` で折る。全体が横長になるなら `flowchart TB`（縦）にする
- **図種は迷ったら `flowchart`** — 状態遷移なら `stateDiagram-v2`、時系列のやり取りなら `sequenceDiagram`、階層と所属なら `flowchart` の `subgraph`
- **色や style は意味があるときだけ** — 「実在しない / 廃止された」の意味づけには `stroke-dasharray: 5 5` が効く。装飾のための色は付けない
## 対象外
チャート・グラフなどデータ可視化のデザイン（チャート種別の選定・配色・軸や凡例の設計）はこの skill の対象外。この skill が扱うのは文章・説明の構造化と図解まで。
